# Адаптация к реальным данным и к новому ТЗ

Система устроена так, что почти любую новую вводную принимают **конфиги и данные, а не код**: импорт → нормализованный конфиг и поток кадров → калибровка модели и автонастройка порогов (ТЗ, раздел 8). Ниже — что делать в каждом случае, по шагам, с командами.

## Быстрая проверка, что всё живо

```bash
npm ci
```

```bash
npm test
```

```bash
npm run dev
```

Интерфейс откроется на http://localhost:5173. Нажмите «×20», дождитесь конца прогрева (минута модельного времени) и кликните по трубе: появится утечка, секундомер покажет время обнаружения.

## 1. Дали параметры трубы

**Таблицей, текстом или PDF.** Есть три пути, и все приводят к одному входному конфигу (`PipelineConfigInput`):

1. **Текст** — в интерфейсе: «Параметры трубы» → «Паспорт трубы текстом». Понимает «Длина: 50 км, диаметр 530×8 мм, нефть 850 кг/м³, давление на входе 3,9 МПа». Диаметр «530×8» — наружный диаметр × стенка, внутренний считается сам.
2. **Таблица «параметр — значение — единица»** (Excel/CSV) — `parsePassportRows` из `@pipetwin/io`, образец `fixtures/import/passport.csv`.
3. **JSON вручную** — скопируйте `configs/pipeline.example.json`. Числа можно писать с единицами (`"530 мм"`, `"39 бар"`, `"60 °C"`, `"45 сСт"`); избыточное давление — `"38 бар изб"`.

Минимум — длина и диаметр. Остальное `resolveConfig` возьмёт из библиотеки (`packages/core/src/config/library.ts`) со статусом **default**: режим перекачки подбирается под скорость 1,5 м/с, датчики ставятся на концах и каждые ~15 км. Статусы видны в интерфейсе (панель «Параметры трубы») и в `ResolvedConfig.params`.

Ошибка в конфиге называет поле и причину: `geometry.diameter: значение должно быть > 0`.

Чтобы новая труба стала основной: положите её в `configs/pipeline.<имя>.json` и запустите стенд с `--config configs/pipeline.<имя>.json`. Интерфейс берёт конфиг из файла (кнопка «Загрузить конфиг трубы»).

## 2. Дали записи датчиков

**CSV, Excel или JSON с замерами.**

```bash
npm run import -- data/их_файл.csv --config configs/pipeline.default.json --out results/frames.csv
```

- Кодировка (UTF-8/cp1251), разделитель, десятичная запятая, служебные строки над таблицей, строка единиц, формат времени (ISO, `dd.mm.yyyy`, дата и время в разных колонках, unix, дата Excel) определяются сами.
- Колонки угадываются по именам и тэгам КИП (PT-101 — давление, FT-201 — расход, TT-301 — температура), единицы — из заголовка (`P_вх, МПа`, `[bar]`) или по величине.
- Без `--mapping` CLI пишет черновик профиля `configs/mappings/<файл>.draft.json` и печатает вопросы (например, «МПа или бар?»). Поправьте черновик, переименуйте в `<имя>.json` и запускайте с `--mapping <имя>`.
- В интерфейсе то же самое делает мастер «Запись с датчиков (replay)»: подтвердите колонки → «Проиграть запись». Профиль можно сохранить кнопкой.

Избыточное давление переводится в абсолютное на этом шаге (`pressureReference` в профиле, по умолчанию `gauge`).

**Записи без утечек** — сразу три пользы:

1. **Шум и смещения** — детектор оценивает их сам по первой минуте любого потока.
2. **Калибровка twin** — кнопка «Откалибровать» (последние 60 с) или в коде:
   ```ts
   calibrate(frames, resolved, { unknowns: ['geometry.roughness', 'thermal.heatTransferCoef'], window: [0, 600] })
   ```
   Параметры, которые не определяются по имеющимся датчикам, остаются `default` с предупреждением (отчёт об идентифицируемости).
3. **Время детекции на их шуме** — сценарий replay с наложенной утечкой (`overlayLeaks`, см. `packages/bench/test/bench.test.ts`):
   ```json
   { "source": { "type": "replay", "file": "data/их.csv", "mapping": "их" }, "overlayLeaks": [{ "t": 300, "type": "leak", "x": 23000, "sizePct": 2 }] }
   ```

**Записи с размеченными утечками** — файл разметки по схеме `schemas/leak-labels.schema.json`, сценарий `{ "source": { "type": "replay", "file": …, "mapping": …, "labels": "data/их.labels.json" } }` в `configs/scenarios/`, затем:

```bash
npm run bench -- --suite files,e3,e5,noleak
```

**Порог под их шум** — `autotune(strategy, leakFreeStream, ctx, { targetFarPerDay: 1 })` из `@pipetwin/detect`: подбирает порог по максимумам статистики на записи без утечки, короткой записи достаточно.

## 3. Другая расстановка датчиков

Это только конфиг (`sensors`). Каждый детектор объявляет требования (`requires`): если датчиков не хватает, он **выбывает с причиной**, а не падает. Например, без расходомеров выбывают D4 и D6, остальные работают; причины пишутся в `results/excluded.csv` и подсказкой в списке стратегий в интерфейсе.

| Что получили | Что происходит |
| --- | --- |
| Только давления | D4, D6 выбывают; twin берёт давления на концах |
| Опрос 1 Гц | Параметры детекторов заданы в секундах — работают; D5 (волна) выбывает (нужно ≥ 5 Гц) |
| Нет датчиков на концах | twin переходит в стационарный режим по доступным замерам; если и их нет — работают D8, D9 (без физики) |
| 50 датчиков | Схема и графики строятся из конфига, подписи не наезжают |

Сколько датчиков нужно для заданного размера утечки — эксперимент E4:

```bash
npm run bench -- --suite e4
```

## 4. Своя метрика жюри

Веса и фильтры выбора — в `configs/selection.json` (TTD, MDL, LOC, FAR, POD, CPU). Поменяйте их и перезапустите выбор, стенд можно не гонять заново:

```bash
python3 python/analysis/select_strategy.py
```

Новая метрика — колонка в `results/runs.csv` (тип `RunRecord` в `contracts.ts`, коммит `contracts:`), расчёт в `packages/bench/src/runner.ts`, учёт в `select_strategy.py`.

## 5. Другая среда, газ, несколько участков

- **Другая жидкость** — `fluid.name` из библиотеки (`light-crude`, `heavy-crude`, `diesel`, `water`) или свои свойства: плотность (`constant`/`linear`), вязкость (`constant`, `filonov-reynolds`, `walther` по двум точкам).
- **Газ** — заготовка: `fluid.phase: "gas"`, плотность по уравнению идеального газа (WP-A9). MOC для газа не реализован; для газопровода — стационарный twin и детекторы D8/D9.
- **Несколько участков, насосные станции** — сейчас один участок с насосом на входе (`boundary.inlet.type: "pump"`) и задвижкой на выходе. Цепочку участков моделируйте отдельными конфигами (граница = давление).

## 6. Свой симулятор или API организаторов

Напишите адаптер к контракту `DataSource` (`packages/core/src/contracts.ts`, раздел 6): `step(dt)` возвращает кадры за интервал, `done` — конец данных. Образцы: `ReplaySource` (`packages/io/src/sources.ts`), `SimulatedSource` (`packages/core/src/plant/source.ts`). Наш plant остаётся для стенда.

## 7. Жёстко заданный стек

- **Обязателен Python-бэкенд** — `python/api` (FastAPI): `/configs`, `/datasets` (тяжёлые форматы через pandas), `/runs`. Расчёт остаётся в браузере.
  ```bash
  uvicorn python.api.app:app --reload
  ```
- **Только Python** — эталон `python/reference/pipetwin_ref.py` с тем же API (стационарный профиль, трение, калибровка), сверен с TS до 0,1% (T-A19). Детекторы переносятся по `packages/detect/src`.

## 8. Добавить детектор (≈ 15 минут)

1. Класс со статистикой в `packages/detect/src/detectors/` (интерфейс `Statistic`: `update(sample) → { score, threshold, … }`, `rearm()`).
2. Запись в `REGISTRY` (`packages/detect/src/registry.ts`): код, требования к датчикам, параметры по умолчанию (в долях σ и секундах), параметр-порог, ранг простоты.
3. Всё. Детектор появится в стенде, интерфейсе и выборе стратегии; порог откалибрует стенд.

## 9. Другие правила рекомендаций

Таблица `configs/actions.json` — правила по порядку, срабатывает первое подходящее. Условия: класс события, доля утечки, уверенность. Подстановки в тексте: `{place}`, `{rate_m3h}`, `{frac_pct}`, `{sensor}`, `{confidence_pct}`. Дадут регламент — замените таблицу, код не меняется.
